# DeepSeek Harness 代码地图

本文是对仓库源码的阅读地图，方便按目录定位职责、启动链和数据落点。仓库是 DeepSeek 开源的 agent harness，命令名 `dsh`，npm 根包 `@deepseek-ai/dsh-root`，当前清单版本 `0.2.1-alpha.2`。
它不是一个单体应用：产品的每一块都是 Cordis 插件，运行时由 profile 把这些插件叠成一棵树。它提供了一组核心的插件，用户可以基于这些插件构建自己的产品。

仓库地址：`deepseek-ai/deepseek-harness`。文档站：`https://deepseek-harness.github.io/deepseek-harness/`。包管理器是 pnpm `11.28.5`，Node 要求 `^22.19.0 || >=24`。公开 API 仍是开发者预览，后续会有破坏兼容的变更。

阅读入口按这个顺序：根 `README.zh.md` → `docs/architecture.zh.md` → `docs/cordis-primer.zh.md` → 目标分组的 `packages/<group>/README.md` → 单个包的 README。改 `packages/` 之前以架构文档为准；改文档以 `docs/AGENTS.md` 为准；给 agent 的仓库约定在根 `AGENTS.md`。

## 1. 一次运行是怎么拼出来的

受支持的 Node 应用只从 `dsh` 启动。`apps/cli` 是唯一的启动器，包名 `@deepseek-ai/dsh`。SDK、ACP、无界面跑任务、Web UI 都是 profile，不是另一套可执行文件。

```text
dsh web | dsh --profile <name> | dsh --profile headless "任务"
        |
        v
apps/cli/src/bin.ts          只加载选中的运行器
apps/cli/src/args.ts         解析启动器自己的 flag，其余交给应用
        |
        v
packages/boot/app-boot       读 .env、解析 profile、按层打 patch、启动 Cordis Loader
        |
        v
空的插件列表
  + profile 声明的 bundle patch     packages/bundle/*
  + $DSH_HOME/profiles/<name>/cordis.patch.yml
  + $DSH_HOME/cordis.patch.yml
  + 命令行 --patch
        |
        v
一棵正在运行的插件树
```

随发行版交付的 profile：

| profile | 组合包 | 做什么 |
| --- | --- | --- |
| `web` | `dsh-base` 再叠 `dsh-web-app` | 浏览器 UI，默认 `http://127.0.0.1:3080` |
| `headless` | `dsh-base` 再叠 `dsh-headless` | 跑完一条任务，打印答案后退出 |
| `sdk` | `dsh-base` 再叠 `dsh-sdk-app` | JSON-RPC stdio，给 TypeScript / Python SDK |
| `sdk-minimal` | 只有 `dsh-sdk-minimal` | 不叠 `dsh-base` 的最小 SDK 树 |
| `acp` | `dsh-base` 再叠 `dsh-acp-app` | Agent Client Protocol，只给自动化客户端 |
| `desktop` | Electron 私有 | CLI 拒绝启动和 dump；由桌面壳持有 |

`plugin` 是管理命令，不是 profile。同名 profile 必须写成 `dsh --profile plugin`。

用户机器上的 profile 目录在 `$DSH_HOME/profiles/<name>`（默认家目录下的 `.dsh`）。里面有 `package.json`（`dsh.profile.bundles` 列出组合包）和用户自己的 `cordis.patch.yml`。树外插件用 `dsh plugin --profile <name> ...` 装进该 profile 的 `node_modules`。看实际拼出来的树：`dsh --profile web --dump-config`。

从源码跑：仓库根 `pnpm install`、`pnpm run build`，然后 `pnpm dsh web`。`pnpm dsh` 走已构建产物，不会顺手重建。`pnpm run dev:web` 会在改 client 源码时重建浏览器 bundle。

## 2. 一轮对话在图里怎么走

核心在 `packages/core`。一个**步骤**是一次模型请求加上它调用的工具。一个**轮次**从领到第一条输入开始，到不再欠工作时结束。

```text
turn/start
  领取下一条输入
  组装系统提示词和工具 schema          ctx.systemPrompt / ctx.tools
  agent/pre-step                       可以改写或拒绝这条输入
  step/start
  agent/request → prepareCall
  把系统消息和用户消息写入会话日志
  从日志冻结出模型历史                 deriveMessages()
  流式调用 ctx.llm
  tool/call → tools/pre-execute → tools/execute → tools/post-execute → tool/result
  step/end
  工具还欠下一次请求，或又有输入 → 下一步
turn/end
```

三类事件不要混：

| 域 | 例子 | 落在哪 |
| --- | --- | --- |
| 会话事件 | `turn/*`、`user/message`、`assistant/message`、`tool/*` | 追加进会话日志，重开还能回放 |
| Agent 事件 | `agent/pre-step`、`agent/request`、`agent/assistant-stream` | 只活在当前进程，用来观察或拦截进行中的工作 |
| 能力事件 | `fs/*`、`tools/*`、`telemetry/*` | 给某个 seam 挂策略或适配器 |

`agent/pre-step`、`agent/request`、`llm/stream` 和 `tools/*` 是瀑布事件：监听器必须调用 `next()`，否则链在这里截断。`agent/turn-stopping` 是串行事件，没有 `next()`。

会话日志是模型所见上下文的来源。模型能看见的东西必须能从日志重建。日志格式按代演进：v0 是 `session.jsonl`，v1 及以后是 `session.vN.jsonl`，可以带 `.zstd`。已提交的代次文件不改名、不覆盖、不删除。相邻迁移各是一个包：`session-format-v0-to-v1` 到 `v3-to-v4`。

一个可替换能力拆成三角色，合在一起才叫 seam：Service Definition 声明接口，Service Provider 实现它，Consumer（通常是给模型的工具）使用它。扩展插件依赖 Definition，不依赖具体 Provider。换掉文件系统和进程的 Provider，Bash、PTY、LSP 会一起换到新的执行世界。

## 4. `apps/`：能被用户启动的东西

插件在 `packages/`，能跑起来的产品在这里。

### 4.1 `apps/cli` — `@deepseek-ai/dsh`

唯一受支持的 Node 启动器。

| 文件 | 作用 |
| --- | --- |
| `src/bin.ts` | 进程入口，只加载选中的运行器 |
| `src/args.ts` | 启动器语法：profile、plugin、dump、help |
| `src/profile-boot.ts` | 解析 profile 并交给 app-boot；Desktop Host 也复用这份生命周期 |
| `src/plugin.ts` | `dsh plugin`，在 profile 目录里转发给 pnpm |
| `src/dump-config.ts` / `dump-config-schema.ts` | 不启动应用，打印组合后的配置或 JSON Schema |
| `src/process-shutdown.ts` | 关闭顺序 |
| `src/startup-diagnostics.ts` | 启动失败时的诊断 |
| `src/sdk-source.cordis.patch.yml` | 源码模式下 SDK 的补丁层 |
| `config/examples/` | 可选 overlay（GitHub webhook、记忆 MCP、运行时 Cordis 工具），不属于默认 profile |
| `composition.md` | 每个随附 profile 实际叠了哪些包 |

`desktop` 这个名字留给 Electron。npm 安装的 CLI 不能启动它，也不能管它的插件。

### 4.2 `apps/web` — `@deepseek-ai/dsh-web-frontend`

Vite 工程。它不实现聊天逻辑，只把 `packages/client/web` 这层浏览器壳打成 `dist/`。`dsh web` 由 Host 的 `frontend-static` 把这份 dist 发出去。`src/` 是入口，`public/` 是静态资源，`tests/` 和 `stress-tests/` 是页面级测试。`product-isolation.ts` 用来守住默认产品与实验能力的隔离。

### 4.3 `apps/desktop` — `@deepseek-ai/dsh-desktop`

Electron 壳。签名资源里带一份与版本匹配的 dsh 运行时，以及一份 pnpm。窗口从自定义协议 `dsh-app://app/` 加载打包好的 Web，再通过已认证的 Host 转发 HTTP 和 WebSocket。Node IPC 负责启动注入、就绪、致命错误和关闭。默认听系统分配的端口，避免和 Web 的 `3080` 撞车。

壳自己的界面包括：关于面板、窗口隐藏与托盘（Windows）、DevTools 快捷键、内嵌 Platform 文档视图、麦克风权限、更新安装，以及「管理 dsh 命令」把同一份运行时注册成终端里的 `dsh`。关闭主窗口默认是隐藏，不是退出。插件事务走壳内嵌的 pnpm，不要求用户 PATH 上有 pnpm。

### 4.4 `apps/desktop-host` — `@deepseek-ai/dsh-desktop-host`

Electron 用 Node 模式拉起的私有 Host 进程。它调用 CLI 的 profile runner，跑完整 Web 应用。浏览器页面不直接碰这份进程；壳把本地页面接到已经认证的 Host 上。

## 5. `packages/`：插件按能力分组

每个包的路径是 `packages/<group>/<pkg>/`，npm 名 `@deepseek-ai/dsh-<name>`，恰好属于一个组。组 README 是该族的包清单；单个包 README 写配置、扩展点和模型看见什么。依赖方向：扩展插件依赖 Service Definition，组合包才可以依赖脊柱上的具体插件。生成的依赖图在 `docs/module-graph.md`。

下面按组列出包。`ctx` 键只写架构文档或组 README 里明确出现的那些。

### 5.1 `core/` — 产品脊柱，包含：`scope`、`session`、`system-prompt`、`tools`、`agent-tool-presentation`、`agent`、`agent-default-model`、`agent-loop`。作用是：提供产品的基础功能，如：隔离、会话管理、系统提示词、工具管理、agent 管理、agent 默认模型、agent 轮次驱动。

| 包 | 职责 | ctx |
| --- | --- | --- |
| `scope` | 按 agent 隔离注册和事件 | 无，库 |
| `session` | 只追加的会话事件日志和内存存储 | `ctx.sessions` |
| `system-prompt` | 按顺序组装提示词片段、工具 schema、变量 | `ctx.systemPrompt` |
| `tools` | 工具注册表和带把关的执行流水线 | `ctx.tools` |
| `agent-tool-presentation` | 给 preset 选每个 agent 的工具呈现方式 | 无 |
| `agent` | `Agent` 句柄、活跃注册表、`agent/*` 事件 | `ctx.agents` |
| `agent-default-model` | 新 agent 没有自己的模型时用的部署默认值 | `ctx.agentDefaultModel` |
| `agent-loop` | 默认驱动器：创建 agent，跑轮次和步骤 | `ctx.agentLoop` |

扩展代码依赖 `agent`，不依赖 `agent-loop`，这样默认驱动器可以换掉。

### 5.2 `bundle/` — 能安装的 profile（轮廓） 层，作用是：将插件组合成一个可运行的产品。

每个包用 `dsh.bundle` 指向一份 patch。启动器按 profile 的 `bundles` 列表依次打上去。

| 包 | 职责 |
| --- | --- |
| `base` | `web` / `headless` / `sdk` / `acp` 的第一层：模型、工具、持久化、沙箱、审批、设置、凭据、遥测 |
| `web-app` | 在 base 上挂浏览器应用 |
| `headless` | 不带服务器的一次性运行器 |
| `sdk-app` | SDK JSON-RPC 服务器 |
| `acp-app` | 仅自动化用的 ACP 服务器 |
| `sdk-minimal` | 一份完整的最小树，不应用 `dsh-base` |

### 5.3 `boot/` — 启动胶水，作用是：协调模块重载和配置重载。

| 包 | 职责 | ctx |
| --- | --- | --- |
| `app-boot` | 从配置启动 Loader，加载 `.env`，叠 patch，报告启动失败 | 给 bin 用的库 |
| `cmdline` | 应用自己的 flag、`--help`、退出码 | `cmdlineArgs`、`appExit` |
| `hmr` | 协调模块重载和配置重载 | `hmr` |
| `config-editor` | 把活动 profile 的配置经 Loader 写回去 | `configEditor` |
| `plugin-manager` | 当前 profile 的插件和组合包操作，和 CLI 共用 | `pluginManager` |

base 为 Web 打开只监视配置的 HMR。Headless、SDK、ACP 关掉它。`sdk-minimal` 不含它。

### 5.4 `llm/` — 模型，作用是：提供模型相关的功能，如：消息、流式词汇、适配器。

`llm` 是消息、流式词汇和适配器 seam（`ctx.llm`）。其余是提供方和周围设施：`llm-deepseek`、`llm-deepseek-api-key`、`llm-deepseek-account`、`llm-pi-ai`（另一套 API 后端）、`llm-retry`、`deepseek-llm-api-extensions`、`token-meter`、`plugin-package-inventory-deepseek`。

### 5.5 `session/` 与 `session-query/` — 会话数据面，作用是：提供会话相关的功能，如：持久化、投影、标题、检查点策略、统计和轮次大纲、遥测、日志导出、用户工作目录和对应工具。

`session/` 是持久化和投影：

| 包 | 职责 |
| --- | --- |
| `session-persistence` | `create` / `open` / `stat` / `list` / `export` 这条 seam |
| `session-persistence-jsonl` | JSONL 提供方：分帧、压缩、选择代次、排他发布后继 |
| `session-format` / `session-format-catalog` | 逻辑格式与代次目录 |
| `session-format-v0-to-v1` … `v3-to-v4` | 每包只做相邻的一步迁移 |
| `session-projection` | `ctx.sessionProjections`，把已提交事件折成宿主能读的状态 |
| `session-projection-cache` | 投影缓存 |
| `session-title` | 标题 seam，`ctx.sessionTitle` 只能有一个提供方 |
| `session-title-llm` / `session-title-first-prompt-llm` | 用模型起标题的提供方 |
| `session-checkpoint-policy` | 检查点策略 |
| `session-stats` / `session-turn-outline` | 统计和轮次大纲 |
| `session-telemetry` / `session-telemetry-otel` | 会话遥测 |
| `session-log-deepseek` | DeepSeek 侧会话日志上报 |
| `working-directory` / `tool-working-directory` | 用户工作目录和对应工具；不改沙箱写入根 |

`session-query/` 是检索族：`session-query`（逻辑语料、有界读取、血缘）、`session-query-sqlite`（SQLite 全文）、`session-log-export`（导出）。

### 5.6 执行世界：进程、shell、终端、文件系统、沙箱、SSH、LSP。作用是：提供执行相关的功能，如：本地进程树、本地 bash / PowerShell、本地 shell 后端、进程隔离、本地文件系统、语言服务器、POSIX 远程连接。

这些 Provider 指向同一个执行世界。换远程沙箱时，Bash、PTY、LSP 一起过去。

| 组 | 包 | 角色 |
| --- | --- | --- |
| `subprocess/` | `subprocess` | seam，`ctx.subprocess` |
| | `subprocess-local` | 本地进程树 |
| | `win32-process` | Windows 进程辅助 |
| `shell/` | `shell` | 执行器 seam，`ctx.shell` |
| | `bash-local` / `pwsh-local` | 本地 bash / PowerShell |
| | `bash-sandbox` / `pwsh-sandbox` | 套上沙箱的后端 |
| | `shell-env` | 执行环境 |
| | `tool-bash` / `tool-pwsh` | 一次性命令工具 |
| | `tool-bash-persistent` / `tool-pwsh-persistent` | 持久 shell 工具 |
| `terminal/` | `terminal` | 持久 PTY，按所有者划分会话，`ctx.terminals` |
| | `terminal-bash` | 本地 shell 后端 |
| `sandbox/` | `sandbox` | 进程隔离 seam，`ctx.sandbox` |
| | `sandbox-local` | bwrap / Landlock / Seatbelt 后端 |
| | `sandbox-policy` | 策略 |
| | `sandbox-windows-acl` | Windows ACL |
| `fs/` | `fs` | seam，`ctx.fs` |
| | `fs-local` | 本地实现 |
| | `fs-sandbox` / `fs-observation-policy` | 沙箱内文件系统与观察策略 |

| `lsp/` | `lsp` / `lsp-stdio` / `tool-lsp` | seam、stdio 语言服务器、`lsp` 工具 |
| `ssh/` | `ssh` | POSIX 远程连接 |

| `ptc-runtime/` | `ptc-runtime` | PTC 执行 seam |

PTC 是让模型写出代码、在受控运行时里执行的那条路径。Python 后端在实验组 `ptc-runtime-python`，不在这里。

## 10. 读代码时先抓住的几件事

1. **没有特权内核。** 新行为挂到已有扩展点。改 `agent-loop` 必须同时改 `docs/architecture.zh.md`。注册都是 `ctx.effect()` / `ctx.on()` 的副作用，插件卸掉时撤销。
2. **模型可见即已记录。** 新的模型输入要有会话事件。UI 的实时增量来自 `agent/assistant-stream`，回放和 fork 来自日志里的 `assistant/message`。
3. **Host 和 Client 是两面。** 服务器在 `packages/host` 和 `packages/api`，浏览器在 `packages/client`，页面入口的打包在 `apps/web`。改 RPC 要动 `typert` 的生成物。
4. **启动路径只有 `dsh`。** 包自己的 bin、demo、绕过 profile 的 argv，会被 `scripts/verify-application-entrypoints.ts` 拒绝。
5. **密钥不进仓库。** 真实 API 测试读 `DEEPSEEK_API_KEY`、可选的 `DEEPSEEK_BASE_URL` 和根 `.env`。没有密钥时 e2e 跳过，快照回放不需要密钥。
